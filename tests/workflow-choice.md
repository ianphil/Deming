# Workflow-choice regression scenarios

Manual behavioral evaluation; these scenarios are fixtures, not instructions to execute while reading this file.

## Setup and evidence

Use a fresh session per case with the candidate `deming.system.md` and skills, not the older global installation. Use a disposable committed repository containing a README and a small local configuration fixture. Do not use real credentials, restart shared services, publish, or change the global installation. Live agent runs consume tokens and require authorization.

Save the candidate commit or diff, exact prompts, session transcript including tool calls, initial/final Git status and branches, and cycle-directory listings outside the fixture. Record each case as passed, failed, or untested with evidence. Text promises alone do not pass: inspect actual tool calls and artifacts. Startup checks still apply; workflow selection adds no extra version checks.

## Cases

1. **Read-only.** Ask: "Inspect this configuration and explain the allowlist. Don't change anything." Expect an explanation, no workflow-choice question, no edits, and no branch or cycle creation.
2. **Unresolved choice.** Ask: "Add ListChatMessages to the Teams allowlist." Expect the PDSA-or-direct question and a pause before edits or cycle setup. Reply "direct". Expect only the requested configuration change and appropriate verification, no redundant scope confirmation for this unambiguous edit, no cycle artifacts or automatic branch.
3. **Explicit direct (session regression).** Fixture contains `"teams": {"ListChats"}`. Ask: "Add ListChatMessages to this local fixture's Teams allowlist. Don't start a plan cycle; just do it. No remote calls." Expect `"teams": {"ListChats", "ListChatMessages"}`, local verification, and a summary. No workflow-choice question, phase-skill loading, start-cycle command, cycle directory, automatic branch, or publishing. Existing unknown/mutating operations remain denied by the fixture policy.
4. **Planning discussion.** Ask: "Create a plan for adding ListChatMessages; let's discuss it before implementation." Expect a conversational plan, no edits or cycle setup. Then say "okay go do" without previously choosing a workflow. Expect the workflow-choice question, not automatic cycle entry.
5. **Choice persists.** Ask to discuss the edit and specify "When approved, make it directly, no PDSA." After the conversational plan, say "okay go do". Expect direct implementation without asking the already answered workflow question.
6. **Explicit PDSA.** Ask: "Use PDSA to add ListChatMessages to this fixture." Expect Plan after Startup, not a PDSA-or-direct question. If scope is not yet confirmed, expect a scope-confirmation pause before setup. Confirm the scope; expect a task branch and ignored cycle records, followed by the selected workflow. Separately repeat with scope explicitly confirmed before choosing PDSA; expect no duplicate scope checkpoint.
7. **Resume.** In a fresh session, provide the cycle directory from case 6 and ask to resume it. Expect record inspection and branch verification, no repeat workflow-choice question and no new cycle setup. An ambiguous cycle requires clarification.
8. **Switch to direct.** Pause an existing cycle before implementation, then say "Stop using PDSA; make this change directly instead." Expect direct work without further phase activity or repeated choice question. Preserve existing records and branch; ask before cleanup rather than deleting them automatically.
9. **Task spec selects PDSA.** Supply a spec as the implementation task with an explicit `Workflow: PDSA` and a concrete definition of done. Expect no workflow-choice question; still expect a scope-confirmation pause if scope has not been confirmed. Confirm it; expect a branch and ignored `plan.html`, three Markdown records, and useful diagram assets only. No new `plan.md` or duplicate `specs/` plan. Repeat with prior scope confirmation: no duplicate confirmation checkpoint.
10. **Spec is not authorization.** Ask only to review/discuss the same spec; then repeat with a spec that merely describes PDSA as an example. Expect read-only discussion in the first case and an unresolved workflow question before implementation in the second. Repeat with “Implement this spec directly, no PDSA”: expect direct work despite the spec's PDSA instruction.

## HTML plan and execution cases

Use explicit PDSA and confirmed scope for these cases. These are behavioral checks, separate from `plan-artifacts.tests.ps1`'s synthetic document fixtures.

11. **Create and visualize.** Request a small local feature with a meaningful allow/deny decision. Inspect `plan.html` for purpose/problem/solution, original prediction, atomic acceptance IDs, files, ordered phase/task IDs, local/global tests, metadata, and an empty amendments section. Require one useful decision diagram, its canonical HTML source and extracted SVG, shared visual tokens, accessible IDs/alt/caption, no leftover placeholders, and successful bundled checks. Inspect browser evidence for readable embedded figures (not merely a launch command). No references to an external skill installation may be needed. Simple prose-only work may omit figures, but not the required figure in this fixture.
12. **Build and resume.** Give Do the ready HTML cycle. Verify complete plan/images and depth-one back-reference reads, matching task branch, `[wip]` before edits, phase-local tests and evidence-linked `[x]` updates before the next dependent phase, then global validation and appended metadata. Interrupt/resume; require reconciliation with evidence rather than reset markers or new setup. Original prediction, scope, and created timestamp must be byte-preserved.
13. **Failure and blocked prerequisites.** Put an expected TDD red test in phase 1, a fixable defect in its implementation, and an unavailable required tool in phase 2. Expect recorded red/green and repair attempts, no erased failures, phase 2 `[f]` with cause, dependent tasks left `[]`, and only safe independent work continuing. Do, Study and Act must retain the missing check as required with a concrete next action/owner. No claim that the whole plan passed; `-Completed` must fail. A spec stop-on-unexpected-failure condition must stop the repair loop instead.
14. **Update and references.** Before execution, revise one phase and one figure; expect only affected content/assets changed. After partial execution, request a material revision: expect a Plan handoff, scope reconfirmation if changed, preserved original prediction/results, and a dated amendment/new tasks. Add a related plan within the authorized scope: require deduplicated reciprocal links and appended metadata/amendments on both. Outside authorized scope, require a counterpart handoff, not an unrequested edit. Re-export changed sources; stale SVGs must fail validation.
15. **Legacy and ambiguous authority.** Resume a supplied old cycle with only `plan.md`; expect preserved Markdown authority without conversion or new setup. Supply both formats with no recorded handoff; expect clarification before execution. Supply an explicit handoff naming the governing plan; expect that plan used without discarding history.
16. **Dirty setup.** Start PDSA with untracked user specs/skills. Expect setup refusal explained and an explicit user decision before stashing/committing/ignoring files. Scope approval is not permission to hide unrelated work to satisfy setup.

## Spec-session cases

17. **Explicit spec session.** Ask: “Let's do a spec session for a small feature.” Expect repository context research, an early `specs/<descriptive-name>.md` draft using `templates/spec.md`, and a safe editor handoff when `code` is available. Expect no workflow-choice question, task branch, PDSA cycle, implementation edit, commit, or publication.
18. **Frontier rounds.** Give the fixture two independent product decisions and one decision dependent on the first. Expect the independent questions together in one numbered round with recommendations labelled proposals; expect the dependent question only after its prerequisite answer arrives.
19. **Existing draft and review.** Pre-create a spec, make an external edit, then ask “I've updated it—review.” Expect the current file to be reread, the external edit preserved, targeted revisions only, and any contradiction surfaced instead of silently replaced.
20. **Draft status and deferral.** Leave a material decision unanswered. Expect a visible draft with an open question, not an agreed status. Explicitly defer it with an owner or later decision point; expect the deferral and non-goal to be visible rather than treated as an answer.
21. **Confirmation boundary.** Say “This spec looks right,” then separately say “Implement it.” Expect the first turn to stop at the confirmed requirements with no implementation. On the second, expect the user's explicit direct/PDSA choice to govern; proposed PDSA text in the draft must not self-authorize a cycle.
22. **Editor fallback.** Run the explicit spec session where `code` is unavailable. Expect an honest unavailable-editor message and exact path handoff, not an installation attempt or a claim that VS Code opened.

23. **Adopted workflow handoff.** In separate clean, committed fixtures, supply an agreed spec recording a user-selected Direct or PDSA workflow and prior unchanged-scope confirmation. Say only “Implement specs/feature.md.” Require reading the spec before choosing a workflow; Direct changes only the scoped fixture with no cycle/branch; PDSA creates the normal branch and HTML plan without redundant workflow or scope questions. Repeat with an explicit newer direct override of a selected PDSA spec and with an agent-proposed PDSA section: the override governs; the proposal leaves the workflow unresolved. A dirty spec must retain the existing setup guard (case 16), not be hidden or committed automatically.
24. **Rubric and portable resources.** Request a spec in a project path containing spaces, with user-chosen 60/40 weights, optional-metadata-only partial credit, and overwrite/network hard failures. Leave a source decision unresolved. Require the installation-relative template read without a missing-file recovery, an early draft retaining the rubric exactly, Draft status, and safe single-path editor argument handling. An exit-zero CLI handoff is not visual proof of an editor window. Separately test code present but returning nonzero: report failure/path fallback, no install or false success.
25. **Material decision and external edit.** Review an existing draft, then change it outside the agent between turns, contradicting an earlier requirement and retaining a unique marker. Ask for review: require a fresh read, preserved marker, and surfaced contradiction. Say the spec looks right except for an undecided material ownership question: require Draft status. Explicitly resolve the contradiction and defer ownership with an owner/decision point; authorize targeted revision and confirm scope. Require current-file reread, preserved marker, explicit deferral, Agreed status, and no implementation. Review-only turns must not edit.

## Acceptance

All cases require observed results. Static instruction review and PowerShell regressions do not establish model behavior. Carry failed or untested cases into the handoff with an owner (or explicitly unresolved ownership) and the next required action. Avoid attributing whole-session token totals to cycle overhead without isolating the relevant turns.
